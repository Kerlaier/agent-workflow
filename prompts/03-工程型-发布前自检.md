# 03 · 工程型 agent —— 发布前自检

> 用途：**任何东西公开发布之前**（仓库、文档、对外材料），逐条过一遍。全部是踩坑换来的。

## 一、脱敏（第一条，硬门槛）

发布前把下面**逐类搜一遍**，出现就删或改：

```text
手机号（1[3-9]\d{9}）        邮箱（xxx@yyy.zzz）
真实姓名 / 昵称              学校、单位、班级
老师与同学的称呼              具体成绩、分数、排名
对某个团队/个人的评价（"大概率去不了""应该没戏"这类）
任何 X:\ 绝对路径（会暴露本机结构）
令牌 / token / 带凭据的仓库地址（remote URL 里可能内嵌 token）
```

> **为什么连"评价"也要删**：泄露的不只是隐私，还有**立场** —— 公开仓库里的一句评价，
> 被当事人看到就是另一种性质的问题。

## 二、事实核对

- [ ] **有没有把"承诺"写成"已完成"？**
      （例：「代码我逐行读懂」是承诺；下一句就会被追问，答不上来比不写更糟）
- [ ] **数字和来源文件对得上吗？**（同一件事出现多个版本 → 先把中间版本作废）
- [ ] **时间戳是实测的，还是随手写的？**（随手写的会直接毁掉"谁先改的"这个判断）
- [ ] **引用的旧记录，现在还是真的吗？**（它描述的对象可能已经被改过）
- [ ] **"检索不到"有没有被当成"从未存在"？**（判历史只能查旧版本 / 备份）

## 三、发布动作

- [ ] **匿名验证**：不带任何凭据访问一次，确认真的公开可看、内容完整。
- [ ] **别把本机 remote 的 URL 抄进文档**（里面可能内嵌 token）。
- [ ] 确认这次改动**没有覆盖**"未经明确说改就不要动"的那些文件。

> 最后一条的现实版本：有一份文档是使用者本人在同时手改的，脚本一跑就会整份覆盖。
> 所以规则是 —— **动手前先问走哪条路，不要默认"重出更干净"**。
