# 工具链与搭建：从一个 AI 搭到三个 AI

> 这份文件是**照着做就能搭起来**的顺序：**先装 → 再定角色和提示词 → 最后建协议与交接文件**。
> **顺序不能换** —— 先建协议再装工具，规矩是空的；先派活再定角色，几个 agent 会抢着改同一个文件。
>
> 文中版本号是**本机实测值**（`npm ls -g --depth=0` 与各工具 `--version` 的输出），不是抄来的。

## 四步总览

| 步骤 | 做什么 | 做完的标志 |
|---|---|---|
| **第一步** | 装三个 AI | 三条命令都能跑出 `--version` |
| **第二步** | 把**教学**交给 Claude，并给它提示词 | 它能按你的要求出讲义和练习 |
| **第三步** | 给另外两个 AI 各自的提示词 | 每个新会话开头就知道自己是谁、该读哪几份文件 |
| **第四步** | 建**协作协议** + **交接文件** | 有了一份规矩、一份状态，三方开始并行 |

## 第一步：装三个 AI

### 1.1 装哪三个

| 角色 | 产品 | npm 包名 | 本机实测版本 | 配置目录 | 形态 |
|---|---|---|---|---|---|
| **教学型** | Claude Code | `@anthropic-ai/claude-code` | `2.1.209` | `~/.claude` | 命令行 + IDE 插件 |
| **工程型** | OpenAI Codex | `@openai/codex` | `0.158.0` | `~/.codex` | 命令行 + 桌面端 |
| **规划型** | DeepSeek Harness | `@deepseek-ai/dsh` | `0.1.0-rc.6` | `~/.dsh` | 命令行 + 桌面端 |

**前置条件**：Node.js + npm（三者都通过 npm 分发）、每个 agent 各自的账号、能连上对应服务的网络。

```bash
node -v     # 本机实测：v24.18.0
npm -v      # 本机实测：11.16.0
```

### 1.2 三条安装命令

```bash
npm i -g @anthropic-ai/claude-code     # 教学型
claude                                  # 首次运行按提示登录

npm i -g @openai/codex                  # 工程型
codex                                   # 首次运行按提示登录

npm i -g @deepseek-ai/dsh               # 规划型
dsh --version
```

登录凭据落在各自的配置目录里（`~/.claude` / `~/.codex` / `~/.dsh`）。桌面端是**另装**的、和命令行**可以并存**。

> ⚠️ **Windows 上的一个真坑：npm 生成的 `.cmd` 外部程序调不到**
> `codex.cmd` 是**批处理文件**，而 Windows 进程创建只认 `.exe` —— 于是**别的程序想调用它时会报「找不到 codex」**。
> 解法：把包内真正的 `codex.exe` 所在目录**追加到用户 PATH**：
>
> ```text
> %APPDATA%\npm\node_modules\@openai\codex\node_modules\@openai\codex-win32-x64\vendor\x86_64-pc-windows-msvc\bin
> ```
>
> **npm 重装或升级这个包时，这条路径可能失效** —— 到时候重新确认一次。

### 1.3 验证装好了

```bash
claude --version
codex --version
dsh --version
```

三条都出版本号 = 第一步完成。

### 1.4（可选，但本项目是这么用的）让 agent 跑在别的模型服务上

**Codex 和 Claude Code 都不绑定单一模型服务** —— 都可以把端点指到别处：

| | 在哪改 | 关键字段 |
|---|---|---|
| **Codex** | `~/.codex/config.toml` | 自定义 `model_provider` + `base_url` |
| **Claude Code** | 启动时的端点相关**环境变量** | 端点地址 / 密钥 |

本项目实际用的是两个**开源**工具 —— 一个负责**转发**，一个负责**切换**：

| 给谁用 | 工具 | 仓库 | 许可 | 做什么 |
|---|---|---|---|---|
| **工程型（Codex）** | **codex++** | [BigPizzaV3/CodexPlusPlus](https://github.com/BigPizzaV3/CodexPlusPlus) | AGPL-3.0 | 在本机起一个服务；Codex 通过 `model_provider` 指向它，它再转发给目标模型服务 |
| **教学型（Claude Code）** | **CC Switch** | [farion1231/cc-switch](https://github.com/farion1231/cc-switch) | MIT | 图形界面，管理 / 切换 Claude Code 的供应商配置（换端点、换密钥），不用手改配置文件 |

`config.toml` 那一侧长这样（**只列相关字段**）：

```toml
# ~/.codex/config.toml
model = "<转发工具提供的模型名>"
model_provider = "custom"

[model_providers.custom]
name = "custom"
base_url = "http://127.0.0.1:<端口>/v1"
wire_api = "responses"
requires_openai_auth = true
```

**模型名填在转发工具那一侧** —— 所以**换模型不用改 agent 的配置**。

⚠️ **三条实话**

1. **转发工具是本机常驻的** —— **它没启动，agent 就起不来**。这是这类搭法最常见的一种"昨天还好好的"。
2. **它看得到你所有的对话和密钥** —— 装之前先确认来源。上面两个都是**公开开源项目**，release 包里的文件哈希**可以自己核对**（本项目核对过：装到本机的 exe 与 release 包内文件**字节一致**）。
3. **合规性自己确认**：用非官方端点去跑某个 agent，可能违反它自己的使用条款。这份文件只讲"**怎么配**"，不对任何第三方服务背书。

## 第二步：把「教学」交给 Claude，并给它提示词

### 2.1 为什么教学给 Claude

**教学是产出最密集的一块**：讲义、练习、参考答案、示例代码、ROS 节点…… 全在这里。
把它交给一个 agent，是为了让**代码只有一个出口** —— 两个 agent 抢着写代码，结果一定是**风格不一致、review 成本翻倍**。

对应地，教学型 agent 的边界是：**写讲义 / 练习 / 代码**，**不碰**计划类文件，**不碰**发布。

### 2.2 教学型提示词（派讲义、派练习任务时一起给它）

```text
出这一课的材料时，按下面来：

1. 练习的「提示」只给思路和关键词，不要给代码。
2. 验收标准是「合上讲义、从空白文件自己写出来」，不是「跑通就行」。
3. 示例尽量贴近真实场景，别用 foo / bar 这种占位。
4. 节奏按 30–45 分钟一站切，一站一个知识点。
5. 材料有更新，告诉工程型 agent 调整时间表。
6. 具体代码统一由你出，工程型 agent 不代写。
```

**每条都对应一次实测出来的问题：**

| # | 条款 | 防的是什么 |
|---|---|---|
| 1 | 提示只给思路 | 「提示」把答案一行一行给全 → **跑通了，但什么也没练到**。判据：提示读完还要动脑 = 合格 |
| 2 | 验收 = 合上讲义自己写 | **「跑通」是个假指标** —— 照着抄也能跑通，所以验收动作必须关掉参考 |
| 3 | 示例贴近真实场景 | `foo` / `bar` / 张三 记不住也建立不起直觉；换成真实场景名词，记忆负担立刻下降 |
| 4 | 30–45 分钟一站 | 人的反馈原话是「不喜欢一天只做一件事」—— 长任务容易疲劳放弃 |
| 5 | 材料变了通知工程型 | 时间表在另一份文件里；不通知 → 时间表会和现实脱节 |
| 6 | 代码只从教学型出 | 两个 agent 抢着写 → 风格不一致、review 成本翻倍 |

## 第三步：给另外两个 AI 各自的提示词

### 3.1 工程型（Codex）—— 发布前自检

**什么时候用**：任何东西**公开发布之前**（仓库、文档、对外材料），逐条过一遍。

```text
发布前自检：

【一、脱敏（硬门槛，出现就删）】
手机号 / 邮箱 / 真实姓名与昵称 / 学校单位班级 / 老师同学的称呼 /
具体成绩、分数、排名 / 对某个团队或个人的评价 / 任何 X:\ 绝对路径 /
令牌、token、带凭据的仓库地址（remote URL 里可能内嵌 token）

【二、事实核对】
- 有没有把「承诺」写成「已完成」？
- 数字和来源文件对得上吗？（同一件事多个版本 → 先作废中间版本）
- 时间戳是实测的，还是随手写的？
- 引用的旧记录，现在还是真的吗？
- 「检索不到」有没有被当成「从未存在」？（判历史只能查旧版本 / 备份）

【三、发布动作】
- 匿名验证：不带凭据访问一次，确认真的公开可看、内容完整
- 别把本机 remote 的 URL 抄进文档（可能内嵌 token）
- 确认这次改动没有覆盖「未经明确说改就不要动」的那些文件
```

> **为什么连"评价"也要删**：泄露的不只是隐私，还有**立场** —— 公开仓库里的一句评价，
> 被当事人看到就是另一种性质的问题。
>
> 最后一条的现实版本：有一份文档是使用者本人在同时手改的，脚本一跑就会整份覆盖。
> 所以规则是 —— **动手前先问走哪条路，不要默认「重出更干净」**。

### 3.2 规划型（第三个 agent）—— 启动提示词

**什么时候用**：**每个新会话开头**直接粘贴。目的是让它在动任何文件之前先"读进状态"。

```text
你是我的第三个 agent，定位是「长期规划 + 情报员」；质检是你的技能、不是岗位；
不写任何成品。

先读这三份文件进入状态：
1. <协作协议>        ← 你的职责与规矩
2. <全局事实文件>     ← 全局状态与决策
3. <长期规划文件>     ← 你的主战场

读完先只做一件事：用三五句话告诉我你接手的现状，然后等我派活。
不要自己改任何成品文件。
```

**每一句防的是什么：**

| 句子 | 防的是什么 |
|---|---|
| 「质检是**技能**、不是岗位」 | 防它把"检查"当主业，变成天天挑刺、不干正事 |
| 「**不写任何成品**」 | 权限边界前置。写权限后置的话，它会"顺手帮你改了" |
| 「**先读这三份文件**」 | 新会话没有上下文；不先读，答案就是泛泛而谈 |
| 「**先只做一件事：复述现状**」 | 这是**准入测试** —— 复述得对不对，一眼看出它读没读懂 |
| 「不要自己改任何成品文件」 | 收尾保险：前面说了规矩，这里再说一遍"现在别动手" |

> 真实教训：「先复述现状」这一步救过场 —— 有一次它复述时把进度说错了，
> 当场就发现它引用的是**旧记录**。没有这一步，错误会直接进规划文件。

### 3.3 质检派单模板（规划型 → 其他 agent）

**什么时候用**：出现"**没人验收的产出**"时，按这个格式派单。

```text
【来自 <谁> · <时间>｜<任务名>】

背景：<一句话说清为什么需要这份核对>

请提供 / 确认下面 N 条：
1. <要什么> —— <为什么要它>
2. …

另：如果 <某个东西> 还有你觉得不实的地方，直接说，我改。
```

**三个关键设计：**

1. **每条都说清"为什么要它"** —— 不说目的，对方会给你一份"看起来很全但用不上"的材料。
2. **最后那句「你觉得不实的直接说，我改」= 给对方否决权** —— 这是整份派单里最重要的一句。
   没有它，对方会倾向于"照着要求交差"；有了它，它才敢说"**你这条要求的前提就是错的**"。
3. **派活判据（三条同时满足才值得派）**：① 当事人自己不会去做 ② 错了会真伤到他 ③ 答案确定、能判对错。

> 反面例子：**当事人自己一眼就能看见的东西**（比如自己文档里敲错一个字），派单是浪费；
> **还没定案的事**也不要派 —— 结论会变，核对出来的东西下一小时就作废。
>
> 核对方**不直接改成品** —— 报告落文件，由 owner 动手。

## 第四步：建协作协议文件 + 交接文件

**到这一步，三个 AI 都装好了、也知道自己是谁了。但它们还是会互相覆盖** —— 因为**没有写权限边界**。
第四步就是补这一层。

### 4.1 先定写权限（这一步是最关键的）

**铁律：每个成品只有一个写手。** 谁都能读，只有 owner 能改。

| 文件 | 归谁写 | 别人可以做什么 |
|---|---|---|
| **协作协议** | 三方共同维护（改动要说明理由） | 读 |
| **全局事实文件（交接文件）** | 工程型 / 规划型 | 读；发现某条事实错了 → **只改那一条** |
| **长期规划** | **规划型（唯一写手）** | 读 |
| **讲义 / 练习 / 代码** | **教学型（唯一写手）** | 读 |
| **质检报告** | 派单方指定 | 读 |

### 4.2 建协议文件

内容 = **写权限边界 + 防打架四条规矩**：

1. **写权限单点** —— 一个成品只有一个 owner
2. **单一事实源** —— 每类事实只有一个权威文件，同一件事不写两遍
3. **结论落文件** —— 核对 / 评审结果写成 `.md` 清单，不靠聊天口头转述
4. **核对事实先看旧版本**（**吃过亏才补的**）—— **检索不到 ≠ 从未存在**

可直接抄：本仓库 `protocol/协作协议.md`。

### 4.3 建交接文件（全局事实文件）

这是**三方的落点**：谁读到它，就知道现在到哪了。

**头部格式（每次改动都要更新）：**

```text
最后更新：YYYY-MM-DD HH:MM（实测时间）｜本次更改：<谁>（一句话）
上一位：<谁>（改了什么）｜建立 / 维护人：<谁>
```

**两条铁律**：

1. 时间戳**只写实测值**；判断先后**看章节号**，不看时间戳。
2. 改法：**只改那一条事实，不整份重写**；动笔前**重读该节**（防覆盖别人的改动）；改完在末尾「更新记录」留一行。

**然后每加一个主题就加一节**：现状 / 决策与为什么这么定 / 踩坑记录（症状 → 根因 → 处置）/ 环境记录。
骨架直接抄：本仓库 `templates/交接文件模板.md`。

### 4.4 建规划文件与报告目录

- **长期规划文件** —— 归规划型，只写"半年后要过哪个关口"这一层。
- **质检报告目录** —— 按需产出。模板：`templates/质检报告模板.md`。

### 4.5 把提示词接上（收尾）

- 把 **3.2 的启动提示词**发给规划型；
- 把 **2.2 的出材料要求**发给教学型；
- 把 **3.1 的发布前自检**发给工程型；
- 每个 agent **第一次启动**，都要求它**先复述现状、再动手**。

## 附一：为什么不装"一个全能的"

- 三个 agent 跑在**同一台机器**、读写**同一批文件** → **人只需要看文件**，不用当传话筒。
- 如果只有一个：它**自己产出、自己记录、自己验收** —— **没有任何独立核对**，错误最后都由人兜住。
- 三个的成本不是钱，是**协调纪律**（本仓库其余部分讲的就是这件事）。

## 附二：关于提示词的存放

上文把提示词**全文抄了一份**，方便照着搭。
**权威版本在 `prompts/`**（那份分文件、带"每句防的是哪次翻车"）—— 两处不一致时，**以 `prompts/` 为准**。

## 附三：常见坑

| 坑 | 症状 | 处置 |
|---|---|---|
| **中转程序没启动** | agent 昨天还好的，今天直接起不来 | 先确认本机中转在跑 |
| **npm 的 `.cmd` 外部调不到** | 别的程序报「找不到 codex」 | 把包内 `codex.exe` 目录加进 PATH |
| **升级后路径失效** | 之前配好的 PATH 突然不灵 | npm 重装/升级后重新确认一次 |
| **并发写同一文件** | 改完不知道丢了什么 | 人肉约定：只改一条 + 动笔前重读该节 |
| **对外说法夸大** | 说成「多智能体系统」会被追问架构 | 统一口径：**一套 AI 协作流程** |

> 装法很普通（三条 `npm i -g`）。难的从来不是装，而是**装完之后怎么让它们不打架**。
